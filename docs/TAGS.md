# ITO 标签集 v1.1

> 适用：内部任务分类、归档检索、巡检整改、维保、值班、授权、人员能力盘点
> 配套：`docs/METRICS.md`、`docs/tags.csv`、`docs/metrics.csv`
> 版本：v1.1 · 2026-11-03 · 200 个标签
> 基准：当前前端实现（`admin.html`、`index.html`、`assets/js/ito-data.js`）+ 内部运维对象补充

## 1. 为什么需要标签集

当前系统不是“缺标签”，而是“标签没有分层”。

| 现状 | 数量 | 问题 |
| --- | --- | --- |
| 任务标签选择器 | 21 个 | 扁平混排，15 个系统代号 + 4 个系统名 + 机房 / 终端 |
| 示例任务实际使用 | 23 个 | 其中 20 个在选择器里选不到 |
| 选择器里从未使用的标签 | 18 个 | 选了也没有业务含义 |
| 成就标签 | 6 个 | 与任务标签口径不同 |
| 人员能力标签 | 4 个 | 核心岗 / 工程师 / KCC / DTT |
| 结构化字段 | 类型、等级、状态、来源、专业组、授权、开票 | 已经能表达的分类，不应再做标签 |

目标：**分层、有定义、可映射、可治理**。标签只表达字段表达不了的交叉属性，不重复字段。

## 2. 三层结构

| 层 | 用途 | 是否可自建 | 示例 |
| --- | --- | --- | --- |
| 业务标签 | 任务、子任务、巡检整改、维保工单的分类与筛选 | 管理员审核后新增 | 防火墙、割接、生产、核心业务 |
| 人员标签 | 人员能力、资质、值班与带班资格 | 管理员审核后新增 | 核心岗、值班、数据库、视频会议 |
| 系统枚举 | 状态、等级、类型、审批、消息、授权等固定值 | 不可自建 | 执行中、紧急、变更、待审批 |

系统枚举只用于展示、筛选和统计，不能当成自由标签使用。

## 3. 七个业务维度

| 维度 | 前缀 | 数量 | 选择方式 | 解决的问题 |
| --- | --- | --- | --- | --- |
| 系统 / 业务域 | `DOM` | 43 | 多选 | 这是哪个系统、哪个业务域的事 |
| 资产 / 对象 | `OBJ` | 46 | 多选 | 动到了什么设备、实例或配置项 |
| 环境 / 范围 | `ENV` | 11 | 多选 | 发生在生产、测试、灾备还是办公环境 |

| 管理 / 协同 | `MGT` | 14 | 多选 | 计划、窗口、通知、验收、复盘等管理属性 |

业务标签合计 **174 个**；人员能力标签单独一层 **26 个**；合计 **200 个**。

## 4. 命名与 ID 规范

- ID 格式：`维度前缀-大写短名`，例如 `OBJ-FIREWALL`、`OPS-CUTOVER`。
- ID 永久稳定；名称可以改，历史数据继续按 ID 解析。
- 名称 2–6 个字；系统代号保留大写，例如 `KCC`、`KNS`。
- 一个概念只允许一个名称；同义词放进“包含”，不另建标签。
- 不使用标点、空格、emoji、序号；不使用“其他”“临时”“杂项”这类兜底标签。
- 每个任务建议 3–6 个标签，硬上限 8 个；内部表格用 `;` 分隔多个标签 ID。
- 标签不重复结构化字段：类型、等级、状态、来源、专业组、授权、开票、开票需求不进标签库。
- 标签默认中性色；只有风险维度和系统枚举使用红 / 黄 / 紫强调色。

## 7. 系统枚举（不可自建）

### 8.5 个人成就口径

个人成就与专业组解耦，按人员累计，数据在 `ito-data.js` 的 `personAchievements`：

- 人员标签：表示个人能力与岗位熟练度，带 1–3 星，最高三星；
- 人员标签星级按该人员完成对应标签任务的次数计算，升星门槛可按标签单独配置，默认 5 次升 2 星、10 次升 3 星；
- 新建人员标签默认 1 星；任务类人员标签记录 `firstClaimed` 首次领取时间，个人统计与成就墙详情都展示；授权关联人员标签为「有 / 无授权」两态，不记录、不展示首次领取时间，授权过期或撤销后从个人标签剔除、重新取得后恢复（默认 3 星）；
- 任务标签：表示个人参与并完成的任务类型，只累计完成次数，不带星级，也没有首次领取时间；
- 同一条标签可以同时作为人员标签和任务标签出现在不同人员档案中；
- 个人统计只取当前登录人的成就，不按专业组汇总；
- 任务标签的展示次数取“种子累计次数”和“当前月完成任务数”的较大值，避免演示数据出现回退。
- 成就墙同时展示人员标签与任务标签；人员标签按人员聚合取最高星级，任务标签只显示完成次数。

## 9. 内部使用规则

### 9.1 打标顺序

内部整理时按固定顺序打标，避免同一件事被打成不同维度：

1. **先定对象**：`DOM-*` 系统域，`OBJ-*` 设备/实例。
2. **再定动作**：`OPS-*` 这次做了什么。
3. **再定影响**：`RISK-*` 可能造成什么后果。
4. **再补环境**：`ENV-*` 生产、测试、灾备、云上、现场。
5. **最后补管理属性**：`MGT-*` 计划、窗口、通知、验收、复盘。

类型、等级、状态、来源、专业组、授权、开票继续用结构化字段，不再打成标签。

### 9.2 打标粒度

- 主任务建议 3–6 个标签，硬上限 8 个；少于 3 个通常说明对象或动作没写清。
- 子任务只补“与主任务不同”的标签；不要把所有主任务标签原样复制一遍。
- 巡检、维保任务用 `OBJ-*` + `OPS-*` + `MGT-*` 表达，不再造“巡检”“维保”动作标签。
- 人员档案用 `SKL-*` 表达能力；需要说明系统熟练度时，可再引用 `DOM-*`。
- 已停用或已合并的标签仍保留在历史记录里，不删除、不改写历史。

### 9.5 暂未覆盖的场景

- AI / 大模型平台
- 边缘节点与边缘网关
- 视频监控存储与 NVR
- 门禁、访客与物理安全
- 备件库存与耗材
- 成本核算与费用分摊
- 供应商绩效评分
- 邮件网关与反垃圾策略

这些场景在出现真实任务后，按“定义、包含、不包含、示例、负责人”的流程新增，不直接塞进现有标签。

| `草稿` | 新提议，尚未评审 | 否 | 否 |
| `启用` | 已评审通过，可被选择 | 是 | 是 |
| `停用` | 不再新增使用，历史保留 | 否 | 是（历史任务） |
| `合并` | 被合并到另一个标签 | 否 | 是（显示新名称） |

- 标签 ID 永久稳定，名称可改；停用和合并都不删除记录。
- 合并必须指定目标 ID，历史引用自动解析到目标 ID，原始 ID 保留在审计日志。
- 停用满 180 天后才能进入归档；归档不影响历史任务展示。

### 10.2 职责与节奏

- 标签管理员（可由平台管理员兼任）：唯一有权新增、改名、停用、合并标签。
- 主管 / 业务负责人：可提议新标签，填写定义、边界、示例和旧标签映射。
- 执行人：只能使用，不能创建。
- 每季度评审一次：清理 90 天未被使用的标签、合并同义标签、补充新系统与新对象。
- 每次变更写入操作日志，保留 180 天；变更内容包括操作人、标签 ID、变更前后名称、原因。

### 10.3 质量规则

- 一个概念只保留一个名称；同义词、缩写、英文名放入“包含”，不另建标签。
- 标签名 2–6 字；系统代号保留大写；不使用标点、空格、emoji、序号。
- 不使用“其他”“临时”“杂项”“未知”兜底标签；无法归类时回到字段或新增有明确边界的标签。
- 标签不重复结构化字段：类型、等级、状态、来源、专业组、授权、开票、岗位。
- 每个任务建议 3–6 个标签，硬上限 8 个；超过 8 个说明标签粒度过细或任务拆分不清。
- 新标签必须有：定义、包含、不包含、适用对象、示例、旧标签映射、负责人。

### 10.4 质量指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 标签覆盖率 | 至少有一个有效标签的任务 ÷ 任务总数 | ≥ 95% |
| 子任务标签覆盖率 | 至少有一个有效标签的子任务 ÷ 子任务总数 | ≥ 90% |
| 平均标签数 | 标签引用总数 ÷ 已打标任务数 | 3–6 |
| 同义标签率 | 被合并或标记为同义的标签 ÷ 标签总数 | ≤ 3% |
| 僵尸标签率 | 90 天内零引用的启用标签 ÷ 启用标签总数 | ≤ 10% |
| 标签使用率 | 近 90 天被使用过的标签 ÷ 启用标签总数 | ≥ 40% |

对应指标 ID 见 `docs/METRICS.md` 的 `DAT` 域。
